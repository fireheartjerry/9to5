# MetaGPT — harvest

## 1. Repo

- **Name:** MetaGPT (`geekan/MetaGPT`), tagline *"The Multi-Agent Framework"*.
- **What it is:** An LLM multi-agent framework that materializes a software-company SOP — assigns roles (Product Manager / Architect / Project Manager / Engineer / QA) that collaborate over a shared message pool to turn a one-line requirement into PRD → design → task plan → code → tests. Core slogan: `Code = SOP(Team)`.
- **Maturity:** High. Widely used (ICLR 2025 oral for AFlow, a commercial product MGX built on it), large surface (roles, DI/Data Interpreter, RAG, experience pool, many ext environments), active. Python 3.9–3.11.
- **Primary language:** Python (pydantic v2, asyncio, llama_index).
- **LICENSE:** **MIT** (`LICENSE`, "The MIT License", Copyright (c) 2024 Chenglin Wu). Permissive — safe to port code with attribution.

## 2. Architecture sketch

- **Team / Environment / Role triad.** `Team` (`team.py`) holds an `Environment` plus a money budget; `Environment` (`environment/base_env.py`) is a shared **message pool** that hosts roles and routes messages by address; `Role` (`roles/role.py`) is an agent with a private observe→think→act loop.
- **Publish-subscribe message routing.** Roles `publish_message` to the env; the env fans out to every role whose `addresses` match the message's `send_to`, dropping it into that role's private `msg_buffer`. Roles `_watch` specific upstream Action types and only react to messages `cause_by` those actions — a content-addressed blackboard, not point-to-point.
- **SOP as wiring.** A role's outputs (e.g. `WritePRD`) are watched by the next role (Architect), whose output (`WriteDesign`) is watched by the PM, etc. The pipeline is encoded purely by who-watches-whose-action; no central scheduler issues steps.
- **Three react modes per role** (`_set_react_mode`): `react` (ReAct LLM-chooses-next-action via a state-machine `_think`), `by_order` (fixed action sequence), `plan_and_act` (build a task plan, then execute tasks). Selectable per role.
- **Structured artifacts via ActionNode** (`actions/action_node.py`): a tree of typed fields compiled into a JSON/markdown schema, LLM-filled, pydantic-validated, then **self-reviewed and self-revised field-by-field against each field's requirement**. This is how PRD/design docs stay machine-parseable between roles.
- **Plan/Task DAG** (`schema.py`, `strategy/planner.py`): tasks carry `dependent_task_ids`; the plan topologically sorts, tracks `current_task`, and `reset_task` recursively invalidates downstream dependents on replan.
- **MGX layer + RoleZero/TeamLeader** (`roles/di/`): a newer command-driven agent core (`RoleZero`) with a TeamLeader that dynamically routes work to named teammates (`publish_team_message`), plus a "quick think" fast-path that skips planning for trivial queries.
- **Cross-cutting services:** RAG engine on llama_index+Chroma/FAISS/BM25 (`rag/`), an **experience pool** with a transparent `@exp_cache` decorator (`exp_pool/`), a cost manager with a hard budget, role serialization/recovery, and capability-scoped external-env APIs (`mark_as_readable/writeable`).

## 4. Top 3 takeaways

1. **The single highest-value steal is the structured-artifact + self-review stack (ActionNode `fill`/`auto_review`/`auto_revise`) combined with the Plan/Task dependency DAG.** Together they attack 9to5's two biggest weaknesses at once: brittle one-shot 7B JSON planning (#1) and shallow marker-presence verification (#2). ActionNode gives schema-validated brain output (replacing loose-JSON salvage) and a per-field "does this output satisfy its requirement?" LLM-judge; the Plan DAG gives real `dependent_task_ids` with topological ordering and cascading `reset_task` replan — exactly the reliable task graph the brief says 9to5 lacks.

2. **The `@exp_cache` experience pool over a llama_index/Chroma RAG engine is a ready-made fix for gaps #4 and #8.** It is a transparent decorator that semantic-queries prior request→response **content** (scored, perfect-judged, context-built) and either returns a past solution or runs and saves the new one. This is strictly better than 9to5's O(n) cosine scan that retrieves metadata-only `lessons_block`s — it persists actual solution content in an ANN index and is wired in with one decorator.

3. **The message-pool + watch/cause_by topology is the architectural pattern for gap #7.** MetaGPT gets coordinated multi-agent collaboration with zero central scheduler: roles publish structured artifacts to a shared pool and subscribe to upstream action types. Adopting this (even just as a blackboard that parallel 9to5 workers read/write structured artifacts through) would let concurrent subtasks exchange results instead of clobbering one shared git tree — and would let adversary remediation run under parallelism, which 9to5 currently disables.

---

**One-line summary:** MetaGPT (MIT, mature) is a high-fit harvest — its SOP role-pipeline rests on three portable mechanisms that hit 9to5's top gaps directly: a pub/sub message pool, a schema-validated self-reviewing ActionNode, a real Task-dependency DAG, and an ANN-backed experience cache.

**Highest-ranked technique:** **ActionNode** (`actions/action_node.py`) — schema-typed LLM artifacts with recursive `fill` + field-level `auto_review`/`auto_revise` against each field's stated requirement; port it to replace 9to5's loose-JSON brain output and add structured spec-vs-output verification.
