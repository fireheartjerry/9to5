# pydantic-ai — Harvest

## 1. Repo

- **Name:** Pydantic AI (`pydantic-ai`), with sub-packages `pydantic_ai_slim`, `pydantic_evals`, `pydantic_graph`.
- **What it is:** A type-safe, Pydantic-native GenAI agent framework — "FastAPI feeling for GenAI" — covering structured/validated outputs, typed tools + DI, durable execution, graphs, evals, and OpenTelemetry instrumentation.
- **Maturity:** Production-grade, very active (Pydantic team), broad model/provider matrix, CI + coverage badges, extensive docs site (`ai.pydantic.dev`).
- **Primary language:** Python (3.9+, heavy typing / `typing_extensions`).
- **License:** **MIT** (`LICENSE`, "Copyright (c) Pydantic Services Inc. 2024 to present"). Safe to port code with attribution.

## 2. Architecture sketch

- **Agent** is the entrypoint; an agent run is internally a **`pydantic_graph` state machine** (`_agent_graph.py`: `ModelRequestNode` → tool/output handling → loop), so control flow is an explicit, inspectable graph rather than a while-loop.
- **Structured output is a first-class, multi-strategy subsystem** (`_output.py`, `output.py`): `ToolOutput` (output-as-tool-call), `NativeOutput` (provider JSON-schema mode), `PromptedOutput` (schema injected into instructions for dumb models), each with its own `OutputProcessor` + Pydantic `SchemaValidator`.
- **Validation failure → retry-prompt loop:** any `ValidationError`/`ModelRetry` from output or tool validation is converted to a `RetryPromptPart` containing the *structured Pydantic error details* and sent back to the model, bounded by per-tool/per-output retry budgets.
- **Tools** are typed callables auto-converted to JSON-schema with a `RunContext` dependency-injection object; **toolsets** compose via decorator-style wrappers (`filtered`, `prepared`, `approval_required`, `prefixed`, `renamed`, `combined`).
- **`pydantic_evals`** is a standalone eval harness: `Dataset` of `Case`s + pluggable `Evaluator`s (incl. `LLMJudge` and OTel `HasMatchingSpan`), concurrency-limited and tenacity-retried, producing reports.
- **Durable execution** wrappers (`durable_exec/temporal`, `dbos`, `prefect`) re-wrap the agent so each model/tool call becomes a durable activity/step, preserving run context/history/retries across process restarts.
- **Observability** is built on **OTel gen_ai semantic conventions** (`_instrumentation.py`): per-request spans with token-usage + cost metrics, plus a queryable `SpanTree` for assertion.

## 4. Top 3 takeaways

1. **The single highest-value steal is the `ValidationError → RetryPromptPart` self-correction loop** (plus the lenient `T | Json[T]` validator and markdown-fence stripping). 9to5's entire planning layer is described as "saturated with fallback scaffolding" because the 7B brain emits bad JSON; pydantic-ai's answer is to validate with Pydantic, then hand the model its *exact* structured field errors and a bounded retry budget. This is a small, MIT-licensed, directly portable pattern that attacks 9to5's root cause rather than papering over it.
2. **`LLMJudge` + the `SpanQuery` trace-assertion DSL together upgrade verification from "markers present in source" to "behavior is correct."** The rubric judge (typed `{reason, pass, score}` with few-shot grounding) is a ready-made spec-vs-diff grader for the adversary; `HasMatchingSpan` over an OTel `SpanTree` lets a verify assert facts about *what actually executed* (exit codes, durations, tool calls) — both named gaps (#2, #5).
3. **For the long-horizon gaps (#1 planning, #3 mid-subtask resume), pydantic-ai shows the destination, not a cheap patch.** `pydantic-graph`'s typed node/decision graph is the structured-planning target, and the `durable_exec` wrappers (Temporal/DBOS/Prefect) are the canonical mid-attempt-checkpoint architecture — model the executor loop as durable, replayable steps. These are heavy ports but worth studying as the reference design before 9to5 builds its own step-journal.

---

**One-line summary:** pydantic-ai is a high-fit, MIT-licensed goldmine for 9to5's JSON-reliability and verification gaps, with strong standout designs for durable execution and typed planning graphs.

**Highest-ranked technique:** the **`ValidationError → RetryPromptPart` structured self-correction loop** (`_output.py:_make_retry_prompt` + `exceptions.py:ToolRetryError._format_error_details`) — feed the brain its exact Pydantic field errors on bad JSON and retry within a bounded budget, instead of 9to5's blind re-prompt + fallback scaffolding.
