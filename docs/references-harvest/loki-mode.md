# loki-mode harvest

## 1. Repo

- **Name:** Loki Mode (by Autonomi, Inc.). npm `loki-mode`, MCP `io.github.asklokesh/loki-mode`.
- **What it is:** A spec-driven autonomous coding agent ("hand it a PRD/issue/OpenAPI/one-line brief, get a verified, tested, deployable Git repo"). Runs a **RARV-C** loop (Reason-Act-Reflect-Verify-Close) with 8 quality gates and a "verified completion" trust layer that refuses to call work "done" on an empty diff or red tests.
- **Maturity:** Very mature / production. v7.101.0, ~1MB CHANGELOG, full release+CI pipeline, npm+Docker+Homebrew distribution, benchmarks (SWE-bench/HumanEval), 41 agent roles, MCP server with 34 tools. This is a real shipped commercial-adjacent product, not a toy.
- **Primary language:** Polyglot. Core orchestration is **bash** (`autonomy/run.sh` ~12k lines, `autonomy/loki` ~23k lines), with a parallel **TypeScript** runtime (`loki-ts/`, the "Bun route" being ported to byte-identical parity with bash), **Python** for memory/swarm/MCP/proof subsystems, and **JS** for observability/integrations.
- **License:** **BUSL-1.1** (Business Source License 1.1), Licensor Autonomi, Inc. Free for personal/internal/academic use; commercial/production use restricted. Source-available, NOT OSI open-source. Harvest = **ideas and patterns**, do not vendor code wholesale into a distributed product.

## 2. Architecture sketch

- **Dual-runtime orchestration.** A bash engine (`run_autonomous()` in `autonomy/run.sh`) is the source of truth; a TypeScript runtime (`loki-ts/src/runner/`) is being brought to byte-identical parity (checkpoint files, JSON separators, etc. all matched exactly). Every TS module documents its bash line-number provenance.
- **RARV-C iteration loop.** Each iteration: build prompt (inject SDLC phase, memory context, queue, checklist, findings) → invoke provider → run quality gates → council vote on completion → checkpoint. Closure adds findings-injection → override-council → auto-learnings → handoff doc.
- **Provider-agnostic dispatch** with tiered degradation: Claude Code (Tier 1, full subagents/parallel), Cline (Tier 2), Codex/Aider (Tier 3 sequential), automatic failover (`loki-ts/src/runner/providers.ts`).
- **Trust layer = the product differentiator.** Deterministic "Evidence Receipt" (`autonomy/lib/proof-generator.py`) separates re-derivable **facts** (git diff sha, test exit code, gate verdicts) from LLM **assessments** (council opinion); the green headline is computed ONLY from facts. A verified-completion evidence gate blocks "done" on empty-diff/red-tests.
- **Multi-agent review** = blind 3-reviewer council from a 6-specialist pool (keyword-selected), Devil's Advocate on unanimous PASS, sycophancy detector, counter-evidence override council, optional BFT consensus + agent-reputation swarm (`swarm/`).
- **3-layer memory** (episodic/semantic/procedural) with vector search, an episodic→semantic consolidation pipeline, cross-project knowledge graph, and a sanitized RAG injector. State lives entirely in `.loki/` filesystem files (checkpoints, queue, signals, events.jsonl).
- **Observability** via OTEL span tree (`src/observability/spans.js`: project→task→rarv→gate/agent/council) plus events.jsonl, efficiency/reward metrics, and a FastAPI dashboard.
- **Anti-reward-hacking** baked in: held-out checklist evals hidden from the build loop, mock-integrity + test-mutation + semantic-test-authenticity detectors, inconclusive-never-green policy throughout.

## 4. Top 3 takeaways

1. **Steal the Evidence Receipt + verified-completion gate first.** This is Loki's whole reason-for-being and it lands squarely on 9to5's biggest verification weakness. The pattern — split every completion claim into deterministic, re-derivable **facts** (git `diff_sha256`, test exit code, gate verdicts) and clearly-labeled LLM **assessments**, then compute the green/amber/red headline ONLY from facts, with "inconclusive is never green" — directly replaces `buildContentScanVerify`'s token-presence theater that a verbose wrong implementation can satisfy. It is a port-code-sized win (`proof-generator.py` is self-contained) and it also gives 9to5 the per-step audit artifact its observability stack lacks.

2. **Loki's real edge is anti-reward-hacking, not raw capability — and 9to5 has the same gameable-brain risk.** Held-out spec evals (reserve 25% of acceptance checks, hide them from the build loop's own prompt, judge only at ship), the counter-evidence override council that fails CLOSED on self-supplied evidence (judge ≠ author), the sycophancy detector, and the spec-then-quality two-stage review all attack the same failure 9to5 is exposed to: the same weak brain authors both the work AND the verify. These are mostly cheap, deterministic, idea-or-small-port techniques.

3. **The multi-agent / long-horizon machinery (swarm BFT, consolidation, span tree) is impressive but mostly heavier than 9to5 needs today.** Harvest the *slices*: agent **reputation tracking** (without the full PBFT protocol), the **Emergence** blackboard primitive, episodic→semantic **consolidation** for experience.db, and the **memory-field prompt-injection sanitizer** (a security hole 9to5 currently has — it injects retrieved lessons raw). Skip wholesale porting of `swarm/bft.py`; its star-topology assumptions don't match 9to5.

---

**One-line summary:** Loki Mode is a mature, BUSL-licensed spec-to-product autonomous builder whose standout contribution is a deterministic *trust layer* (facts-vs-assessments Evidence Receipt + verified-completion + held-out evals) that directly fills 9to5's shallow-verification gap.

**Highest-ranked technique:** the **Evidence Receipt** (`autonomy/lib/proof-generator.py`) — a forge-proof completion proof whose green headline derives only from re-derivable facts (diff sha, test exit code, gate verdicts), with LLM opinions explicitly fenced off as non-binding assessments.
