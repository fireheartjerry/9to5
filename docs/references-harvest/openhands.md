# OpenHands (Agent Canvas) — Harvest

## 1. Repo

- **Name:** OpenHands / Agent Canvas (formerly OpenDevin).
- **What it is:** Self-hosted control plane for running coding agents (OpenHands, Claude Code, Codex, Gemini, any ACP agent) inside isolated sandboxes, with conversations, events, automations, and integrations.
- **Maturity:** High — large, active, production project (OpenHands Cloud/Enterprise run on it); README marked beta for this Canvas rewrite.
- **Primary language:** Python (FastAPI app-server) + TypeScript frontend.
- **License:** **MIT** for everything outside `enterprise/` (that dir has its own commercial license). Root `LICENSE` confirms MIT.
- **IMPORTANT caveat:** This checkout is the **app-server / control plane only**. The actual agent loop, `Event` types, runtime, and condenser internals were moved to the external `OpenHands/software-agent-sdk` (imported as `openhands.sdk` / `openhands.agent_server`, *not* vendored here). So the deepest agent-controller/condenser code is **not readable in this repo** — we harvest the orchestration/isolation/event/compaction-config layer that *is* here.

## 2. Architecture sketch

- **Control-plane / data-plane split:** the app-server (this repo) never runs agent code. It provisions a **sandbox** (Docker container or local process) that runs an `agent-server`; all edits/tests happen there. The app-server talks to it over HTTP.
- **Event stream is the source of truth.** Every agent action is an `Event` persisted per-conversation via a pluggable `EventService` (filesystem / SQL / S3 / GCS backends), queryable, paginated, and replayable as a trajectory.
- **Webhook callback loop:** the sandbox POSTs each event back to the app-server (`/api/v1/webhooks`, URL injected as a container env var). Registered `EventCallbackProcessor`s fire side-effects (set title, detect automation triggers) with retry + result tracking — a decoupled pub/sub over the event stream.
- **Everything is a swappable `Injector` service.** Sandbox, event store, callbacks, conversation info, start-tasks each have an abstract base + multiple backend impls selected by dependency injection (`process` vs `docker` vs `remote`; `filesystem` vs `sql` vs cloud).
- **Context compaction via SDK condenser:** conversations are built with an `LLMSummarizingCondenser` (`max_size` + `keep_first`), with a **dedicated condenser LLM** tagged by `usage_id` so its cost is attributed separately from the agent.
- **Per-role cost attribution:** every LLM (agent / condenser / planning_condenser) carries a `usage_id` + litellm metadata (conversation_id, user_id) so spend is broken out per role and per conversation.
- **Capability scoping by proxy:** the sandboxed agent never holds git creds; privileged actions (PR/MR creation across GitHub/GitLab/Bitbucket/Azure) are proxied through a server-side **MCP** surface that holds the tokens.
- **Repo-sourced skills/hooks:** skills (micro-agents) and hooks are loaded per-conversation from `.openhands` / `.agents` repos at user/org/project/public layers, keyword- or slash-triggered.

## 4. Top 3 takeaways

1. **The event stream is the spine, and it fills two 9to5 gaps at once.** OpenHands makes every agent step a persisted, queryable, replayable `Event` with a pluggable store and a `webhook → EventCallbackProcessor` pub/sub on top. Adopting this gives 9to5 both the **mid-subtask step journal** (gap #3 — resume/replay from last event instead of re-running the subtask) and **structured tracing/alerting** (gap #5) from one mechanism. This is the single highest-leverage steal.

2. **Sandbox isolation is a solved, swappable interface here.** One `SandboxService` abstraction backs Docker, local-process, and remote impls with health-check grace, port exposure, session-key auth, eviction caps, and **MCP credential proxying** so the agent never holds secrets. 9to5 (running `--dangerously-skip-permissions` on the real tree) can port the *process/worktree* variant cheaply now and the Docker variant later, gaining gap #6 without rewriting the executor.

3. **Compaction and cost are first-class and per-role.** Long-horizon context is handled by an `LLMSummarizingCondenser` (`max_size`/`keep_first`, separate condenser LLM), and *every* LLM role (agent/condenser/planning) carries a `usage_id` + metadata for per-role, per-conversation cost attribution. This is exactly 9to5's gap #8 (rolling summarization vs hard truncation) plus gap #5 (consistent cost series) — and the `usage_id` tagging is trivially portable even though the condenser body lives in the external SDK.

---

**One-line summary:** OpenHands' app-server is a high-value control-plane harvest — event-stream-as-journal, swappable Docker/process sandboxes, condenser-based compaction, and per-role cost attribution map cleanly onto 9to5 gaps #3/#5/#6/#8 (deepest agent-loop/condenser code lives in an external SDK not in this checkout).

**Highest-ranked technique:** the **durable per-conversation event stream + webhook callback processors** (`openhands/app_server/event/event_service_base.py`) — one mechanism delivers both the mid-subtask step-level resume journal (gap #3) and structured step tracing/alerting (gap #5).
