# Theme: Long-Horizon Durability

*Checkpoint/resume · step-level journals · pending-writes · crash-safety · time-travel · transactional state · auto-commit-as-journal*

Cross-repo synthesis over the 23-repo agent-tech harvest. Read-only; all paths verified against the digests and (where noted) the vendored source under `C:\9to5\references\<repo>`.

## 1. Intro — the theme and how 9TO5 handles it today

Long-horizon durability is the set of mechanisms that let a long-running agent survive a crash, kill, deadline, or process restart **without losing or redoing completed work** — and, ideally, replay or undo it. The spectrum runs from coarse (snapshot the whole run state periodically) to fine (a write-ahead log of every individual step, replay-skipping completed ones on resume), plus the adjacent capabilities those journals unlock: time-travel/fork, run-wide undo, and failed-attempt replay-debugging.

**9TO5 today (from `_9to5-brief.md` §2.2).** 9TO5 already has a *competent subtask-granularity* durability layer: `platform_core/runtime/resilience.py::run_with_recovery` wraps the run (crash → reload persisted state, which is the source of truth → exponential-backoff resume with a progress-aware, horizon-scaled restart budget ≈1 retry/15 min), with deadline awareness, orphan resume (`pick_resume_task`), and stall detection (`is_stalled`). State is checkpointed at **subtask granularity** — every `TaskState` mutation calls `save()` (`state/task_schema.py`). Resume un-strands `in_progress` subtasks back to `pending` and rebuilds the architect doc from Obsidian (`run_phase_mixin.py::_resumeSetup`). Within a subtask, Claude sessions are carried across retries via `--resume <session_id>` (`agents/executor.py`), and a livelock guard aborts after 40 no-progress iterations.

**Where it's weak (gap #3, a top-3 priority).** There is **no mid-subtask checkpoint**. A crash or kill mid-attempt loses the entire attempt; resume restarts that subtask from scratch (status flips `in_progress`→`pending`). There is **no durable step-level journal** of what the executor actually did — only the final Obsidian note + the `experience.db` row. `--resume` is best-effort and discarded on any error (`execute_mixin.py` keeps `resume_session` only when `not is_error`). There is no transactional/WAL execution log to replay a partially-completed subtask, and no run-wide undo beyond the git snapshot inside adversary remediation. Notably, 9TO5 *already taps the executor's per-tool-call stream* (`notifications/subprocess_feed.py` parses Claude stdout JSONL into tool events) — so the raw signal for a step journal exists but is consumed only for presentation, not persisted as resumable state.

The harvest is unusually rich here: durability is the single most-converged theme across the corpus. Two dominant design families appear repeatedly — (A) a **pending-writes / WAL journal** (LangGraph, SwarmClaw, MS Agent Framework, CrewAI, guild, dify), and (B) **commit/snapshot-per-mutation as the journal** (Loom auto-commit, Claude Code file-history, Hermes shadow-git, AGX git-patch store) — plus (C) **durable turn/step state machines keyed by run-id** (eliza Smithers, pydantic-ai durable_exec, dify pause/resume).

**Dedupe notes.** Techniques #1/#6/#8/#9 are the *same core idea* — a transactional per-step log you replay on resume — expressed over different stores (LangGraph/SwarmClaw = `writes` table; MAF = superstep snapshot; CrewAI/guild = SQLite-WAL rows; OpenHands/dify = event stream). **LangGraph is the cleanest design and SwarmClaw the most directly portable code** (already SQLite, already a Claude-Code-class runtime). Techniques #2/#3/#7 are the *commit/snapshot-per-mutation* family; **Claude Code #3 wins for 9TO5 specifically because 9TO5 already runs that exact binary** (it's a config + tap, not a rebuild), with **Loom #2** as the cleaner conceptual model if 9TO5 wants its own infra-level layer. #5 (eliza/pydantic) is the heavyweight "model the whole executor as a durable workflow" destination. #11/#12 (time-travel/fork, record-replay) are the same replay-debugging capability that any journal unlocks once it exists.

## 3. If 9TO5 adopts ONE thing for this theme

**Persist a pending-writes step journal from the executor stream 9TO5 already taps, and resume from the last completed step instead of restarting the subtask.** Concretely: extend `notifications/subprocess_feed.py` (which already parses Claude's stdout JSONL into per-tool-call events) to *durably append* each completed executor step as a row in `state/experience.db`, keyed `(run_id, subtask_id, attempt, step_idx)` — the exact shape of **LangGraph's pending-writes table** (`checkpoint/.../base/__init__.py` `put_writes`), for which **SwarmClaw's `src/lib/server/langgraph-checkpoint.ts` is a ready, SQLite-native port**. Then change the resume path in `run_phase_mixin.py::_resumeSetup` / `resilience.py` so that an interrupted `in_progress` subtask does **not** flip back to `pending`; instead it reconstructs an **AGX-style step-level resume prompt** (`lib/prompts/resume.js`: `[x]/[→]/[ ]` markers + a "continue from the current step, don't rewrite the plan" stability footer) and re-invokes the executor with `--resume <session_id>` carried robustly. This is the highest-leverage move because it is the **single most-converged technique in the entire corpus** (rank-5 in LangGraph, SwarmClaw, and MAF; rank-5 equivalents in CrewAI/guild/eliza), it reuses three things 9TO5 already owns (the JSONL tap, the SQLite ledger, and `--resume`), and it directly closes the brief's #3 gap — turning a crash mid-attempt from a full-subtask redo into a replay-skip of completed steps — while laying the journal foundation that later unlocks failed-attempt replay (bernstein) and run-wide undo. Pair it cheaply with **Loom/Claude-Code auto-commit-per-edit** so the file tree and the journal stay consistent on rollback, and add **MAF's graph-signature-hash gate** so a resume is rejected if the plan or loop code changed underneath it.
