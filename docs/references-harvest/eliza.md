# eliza harvest

## 1. Repo

- **Name:** elizaOS (`@elizaos/*` monorepo).
- **What it is:** an open-source, local-first "agentic operating system" — a model-agnostic agent runtime plus a desktop/mobile/web AI assistant, CLI, dashboard, cloud backend, native OS forks, and ~80 first-party plugins.
- **Maturity:** very high. Large, active, productionized monorepo (Bun/Node24, Turbo, Vitest, Biome), bootable OS targets, npm-published packages, a binding `PR_EVIDENCE.md` "prove it with live trajectories" shipping standard, heavy test coverage and issue-tracked epics.
- **Primary language:** TypeScript (ESM-only).
- **License:** **MIT** (`LICENSE`, "Copyright (c) 2026 Shaw Walters and elizaOS Contributors").

Note: eliza is a *chat-assistant* framework, not a coding-task orchestrator like 9TO5 — but its `plugin-agent-orchestrator` (spawn coding sub-agents, grill them until done) and `packages/core` runtime are a near-perfect domain match for 9TO5's executor/verifier/orchestrator loop. The relevant code is concentrated and high-quality.

## 2. Architecture sketch

- **Plugin primitive model:** every capability is a `Plugin` exporting four primitives — **actions** (do things, validate+handler), **providers** (inject prompt context), **services** (long-lived singletons), **evaluators** (post-response work) — plus routes/events/model handlers. Clean seam for replaceable intelligence.
- **Model-agnostic core (`@elizaos/core`):** the agent loop, message/memory/state primitives, a native-tool-calling **planner loop** with trajectory + repeated-failure limits, and a model layer abstracted over OpenAI/Anthropic/Gemini/local Eliza-1.
- **Agent-orchestrator plugin:** spawns local coding CLIs (claude/codex/opencode/elizaos) over **ACP** (Agent Client Protocol, JSON-RPC), routes their `task_complete`/`error`/`blocked` events back into the runtime as synthetic messages, and owns workspace lifecycle + GitHub PR integration. This is the analog of 9TO5's Executor+Verifier+Replanner.
- **"Grill until truly done" verification stack:** acceptance-criteria generation → typed completion-evidence assembly → structured CompletionEnvelope contract → small-model goal judge → independent read-only execution verifier → bounded verify→correct loop.
- **Durability via Smithers:** a coding task is modeled as a durable workflow (provision → durable turn loop → approval gate → submit) with per-step/per-turn SQLite state; re-running with the same `runId` resumes a crashed run from the last completed turn.
- **Observability:** a JSON-file **trajectory recorder** writes a per-run span tree (stage kinds: planner/tool/evaluation/subPlanner/compaction) with per-call token usage + USD cost from a price table; spawns propagate parent→child step ids for cross-process distributed tracing.
- **Long-context machinery:** `model-input-budget` (window-scaled compaction reserve + `shouldCompact` threshold) and **RLM** (Recursive Language Model: peek/grep/partition/map_subcall/summarize/stitch over oversized contexts under an explicit budget).
- **Isolation & control:** scratch-dir workspaces with TTL GC + path-scoped safe-remove, remote plugins in isolated Bun worker/subprocess with an RPC `RuntimeProxy`, build-variant sandbox policy, capped self-spend allowance, pure-reducer loop guards, idle/stall watchdog, and an interruption decider.

## 4. Top 3 takeaways

1. **The verification stack is the single biggest steal.** eliza's `plugin-agent-orchestrator` independently solves 9TO5's #2 gap (shallow verify) with a coherent, portable chain: auto-generate measurable **acceptance criteria** → assemble **typed completion evidence** (real git diff + mined test/build output + loopback-flagged URLs) → demand a structured **CompletionEnvelope** (commands with real exit codes, per-criterion evidence) → judge it with a cheap **LLM goal verifier**, and crucially escalate to a **separate read-only verifier agent that confirms by execution, not narration** (Agent-as-a-Judge). Each piece is a pure-ish, unit-tested module — port them roughly in this order.

2. **Durability and tracing have ready-made models.** The **Smithers durable task runner** (task = durable workflow with per-turn SQLite state, resume by `runId`) is exactly the mid-subtask checkpoint/journal 9TO5 lacks (#3), and the **trajectory recorder** (JSON span tree with stage kinds + per-call token/USD cost from a price table, plus parent→child spawn linking) is the structured, cost-aware trace 9TO5's presentation-heavy observability is missing (#5).

3. **Smaller pure-function patterns are cheap, high-leverage wins.** `router-loop-guard` (one immutable reducer for all runaway-loop accounting, fuzz-testable), `task-watchdog` (idle-stall + approaching-cap detectors), `model-input-budget` (window-scaled compaction trigger), `spend-allowance` (risk-classed budget-bounded autonomy), and `interruption-decider` (mid-run human steering) are each small, dependency-light, and map onto existing-but-weaker 9TO5 mechanisms (livelock guard, fixed num_ctx truncation, gate-only human loop).

---

**One-line summary:** eliza (MIT, mature TS agent OS) is a near-perfect domain match — its `plugin-agent-orchestrator` verification chain and `core` durability/tracing fill 9TO5's deepest gaps; highest-ranked steal = the **CompletionEnvelope + independent execution-grounded verifier (Agent-as-a-Judge)** in `plugins/plugin-agent-orchestrator/src/services/{completion-envelope,independent-verifier,goal-llm-verifier}.ts`, which replaces 9TO5's "markers exist in source" verify with a second agent that re-runs the tests and judges per-criterion evidence.
