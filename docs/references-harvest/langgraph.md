# LangGraph — harvest

## 1. Repo

- **Name:** LangGraph (`langchain-ai/langgraph`), monorepo under `libs/`.
- **What it is:** Low-level orchestration framework for building durable, stateful, multi-actor agents as graphs/state-machines whose execution is checkpointed at every super-step so runs can pause, resume, time-travel, and survive crashes.
- **Maturity:** Very high. Production framework (used by Klarna, Replit, Elastic), versioned to v1.x, broad test suite, multiple storage backends, conformance test library (`checkpoint-conformance`).
- **Primary language:** Python (parallel JS/TS SDK in `sdk-js`; CLI; Python/JS server SDKs).
- **License:** **MIT** (`LICENSE`, Copyright 2024 LangChain, Inc.).

## 2. Architecture sketch

- **Pregel/BSP execution model** (`libs/langgraph/langgraph/pregel/`): the graph runs in discrete *super-steps*. Each step selects actionable nodes (tasks), runs them in parallel, collects their writes, applies them to channels, then checkpoints. This is a deterministic message-passing loop, not an ad-hoc agent loop.
- **Channels = typed state cells with reducers** (`langgraph/channels/`): `LastValue`, `BinaryOperatorAggregate` (reducer e.g. `operator.add`), `Topic`, `EphemeralValue`, `DeltaChannel`. State updates are *channel writes*; reducers merge concurrent writes.
- **Checkpoint = immutable state snapshot** (`libs/checkpoint/.../checkpoint/base/__init__.py`): a `Checkpoint` TypedDict holds `channel_values`, `channel_versions`, and `versions_seen` (per-node map of which channel versions a node has already consumed). `versions_seen` is what makes "which task runs next" deterministic and idempotent across resumes.
- **Checkpointer = pluggable persistence** (`BaseCheckpointSaver`): `put`/`put_writes`/`get_tuple`/`list` over `(thread_id, checkpoint_ns, checkpoint_id)`. Concrete: `InMemorySaver`, `SqliteSaver`/`AsyncSqliteSaver`, `PostgresSaver`. Two tables: `checkpoints` and `writes` (pending intermediate writes).
- **Store = long-term cross-thread memory** (`libs/checkpoint/.../store/base/`): hierarchical-namespace KV with optional vector/semantic search (`IndexConfig` = `dims`+`embed`+`fields`, plus TTL), filter operators, pagination. Separate from checkpoints (which are per-thread short-term state).
- **Interrupt/Command HITL** (`langgraph/types.py`): `interrupt(value)` raises a resumable `GraphInterrupt`; the run halts durably; client resumes with `Command(resume=...)`. Node re-executes from the top but completed task results are replayed from the checkpoint.
- **Two authoring surfaces:** declarative `StateGraph` (`graph/state.py`) and imperative Functional API (`func/__init__.py`: `@entrypoint`/`@task` with durable `previous` state and `entrypoint.final`).
- **Time-travel:** `get_state_history()` lists every past checkpoint; `update_state()` forks a new branch from any checkpoint (`source="fork"`), enabling replay/what-if and edit-then-resume.

## 4. Top 3 takeaways

1. **The pending-writes journal is the single highest-value steal.** LangGraph's separation of `put_writes` (durable, per-task, pre-commit) from `put` (super-step checkpoint commit), keyed by `(thread, checkpoint, task_id, idx)`, is a textbook WAL for agent execution. It is precisely 9to5's gap #3: instead of flipping `in_progress→pending` and re-running the whole subtask after a crash, 9to5 could persist each completed ExecutionStep's result and replay-skip it on resume. The SQLite `writes` table (≈8 columns) is small and portable into `state/experience.db`.

2. **Checkpoint + Store cleanly split short-term vs long-term memory — and both beat 9to5's current stores.** Per-thread `Checkpoint` (versioned channel state, time-travel, fork) is the durable run state; the cross-thread `Store` with hierarchical namespaces + vector `IndexConfig` is the persistent, content-bearing, ANN-searchable memory 9to5 lacks (gap #4). Adopting the Store's namespace+embed+filter+TTL shape would replace both the O(n) cosine scan and the metadata-only `lessons_block` with real solution-content retrieval.

3. **`interrupt()`/`Command(resume)` + time-travel give durable HITL and replay almost for free once you have checkpoints.** Because resume re-enters a node and replays completed task results, LangGraph gets inline human approval (gap #8), failed-attempt replay, and edit-and-retry (`update_state` fork) as derived features of one persistence model — versus 9to5's coarse plan/pre_pr gates and presentation-only replay. The `HumanInterrupt` schema (`allow_ignore/respond/edit/accept`) is a ready vocabulary for per-step Discord approvals.

---

**One-line summary:** LangGraph (MIT, production-grade) is a checkpoint-everything BSP graph runtime whose persistence model maps almost 1:1 onto 9to5's durability (#3), HITL (#8), and RAG-memory (#4) gaps.

**Highest-ranked technique:** the **pending-writes journal** (`put_writes` + `writes` table) — a per-task write-ahead log that lets a crashed/killed subtask resume from its last completed step instead of restarting, directly closing 9to5's mid-subtask checkpoint gap.
