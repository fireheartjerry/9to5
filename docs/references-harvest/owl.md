# OWL — harvest

## 1. Repo

- **Name:** OWL — *Optimized Workforce Learning for General Multi-Agent Assistance in Real-World Task Automation* (CAMEL-AI).
- **What it is:** A thin orchestration layer on top of the CAMEL-AI framework that wires a society of role-playing / "workforce" agents (a coordinator + a task decomposer + specialized tool-equipped workers) to solve open-ended real-world tasks; best known for topping the open-source GAIA leaderboard (~69%).
- **Maturity:** Active, research-backed (arXiv 2505.23885, May 2025; HF model checkpoints + training data released Jul 2025), but the *repo itself* is mostly demos + a benchmark harness. Almost all real machinery (`RolePlaying`, `Workforce`, `ChatAgent`, toolkits, MCP) lives in the `camel-ai==0.2.84` dependency, **not** in this tree. Version `0.0.1`.
- **Primary language:** Python (>=3.10,<3.13). Gradio web UI.
- **License:** Apache-2.0 (`licenses/LICENSE`, `pyproject.toml` `license = "Apache-2.0"`). Permissive — code is portable into 9TO5 with attribution.

> Caveat for the harvester: OWL's own code surface is small (~6k lines, half of which are 4 near-duplicate Gradio webapps). The interesting *patterns* are CAMEL's `Workforce`/`RolePlaying`, which OWL configures and prompt-engineers. Techniques below are judged on the **patterns OWL demonstrates**, since 9TO5 would re-implement the idea, not vendor CAMEL.

## 2. Architecture sketch

- **Dual-agent role-play loop** (`owl/utils/enhanced_role_playing.py::OwlRolePlaying`): a *user* agent (instructor/planner, no tools) and an *assistant* agent (executor, holds all toolkits) take strict alternating turns. User emits exactly one `Instruction:`; assistant replies `Solution:`; loop ends when user emits the sentinel `<TASK_DONE>`. This is iterative decomposition-by-dialogue rather than an up-front plan.
- **Workforce topology** (`examples/run.py`): a `Workforce` holds a `coordinator_agent` (assigns subtasks to the best worker) + a `task_agent` (decomposes the task into subtasks) over a roster of **specialized single-purpose workers** — Web agent, Document-processing agent, Reasoning/Coding agent — each with its **own model instance and a scoped toolkit list**. `workforce.process_task(task)` runs decompose → assign → execute.
- **Per-worker prompt specialization:** each worker's system prompt is a long domain playbook (search heuristics, "check Wikipedia first", "never trust a failed tool's output", "run the code you wrote", "verify the final answer with a second tool").
- **Turn-level context re-injection:** every round re-appends the *overall task* as `<auxiliary_information>` and an anti-procrastination rule ("never say 'I will…', call the tool first and report which tool you called").
- **Answer-format enforcement + deterministic scoring** (`OwlGAIARolePlaying` + `gaia.py`): on `TASK_DONE`, the assistant is forced to emit `<analysis>…</analysis>` and `<final_answer>…</final_answer>`; `GAIABenchmark.question_scorer` then normalizes (numbers/lists/strings) and exact-matches against ground truth.
- **Token accounting:** `run_society` sums prompt/completion tokens per round and records a `chat_history` of `{user, assistant, tool_calls[]}` dicts.
- **Toolkit layer:** rich tool surface incl. `DocumentProcessingToolkit` (chunkr → crawl4ai fallback chain, unzip, multimodal), MCP integration, code-execution sandbox (`CodeExecutionToolkit(sandbox="subprocess")`).
- **GAIA harness:** resumable benchmark runner (skips already-completed `task_id`s, checkpoints results JSON after each task).

## 4. Top 3 takeaways

1. **The Workforce pattern is the one genuinely worth stealing** — a `task_agent` (decompose) + `coordinator_agent` (assign) routing subtasks to a roster of *specialized workers, each with its own model and a scoped toolkit*. It directly addresses two 9TO5 gaps at once: richer multi-agent topology (gap #7) and per-agent capability scoping (gap #6/2.8). It's an architecture idea, not vendorable code (it lives in CAMEL), but it's a clean blueprint for evolving 9TO5 beyond the star topology + Claude-subagent fan-out.
2. **The dual-agent instruct/solve loop is a credible answer to 9TO5's brittle one-shot planner.** Decomposition emerges turn-by-turn from a planner agent that issues one instruction at a time, with task re-injection, anti-procrastination, and self-verification reminders baked into every turn — robust on a weak brain and requiring no valid up-front JSON task graph. The prompts + loop are ~250 lines of Apache-2.0 code that could be ported almost verbatim.
3. **Most of OWL is demos/Gradio, and its verification is shallow** (format-tag enforcement + exact-match scoring tuned for GAIA's short factual answers) — it does *not* solve 9TO5's deeper semantic-verification, durability, or RAG gaps. Harvest the orchestration *patterns* (Workforce, role-play loop, per-worker scoping, verify-with-a-second-tool reminder), not the code wholesale.
